# Govor Server

Серверная часть мессенджера Govor.

## Введение в тесты на Python

Ниже описан рабочий подход к тестированию в этом проекте. Он сделан так, чтобы на реальных примерах было видно, зачем нужны фикстуры, фабрики, dependency override и как писать хорошие тесты.

### 1. Зачем вообще нужны тесты

Тесты нужны не «чтобы было красиво», а чтобы:

- быстро находить ошибки;
- не ломать уже работающую логику после изменений;
- документировать ожидаемое поведение приложения;
- проверять, что API и БД работают согласованно.

Главная идея: тест должен отвечать на вопрос «что должно происходить в реальной системе?».

---

### 2. Что такое pytest fixture

`pytest.fixture` — это подготовка окружения для теста.

В проекте они находятся в [tests/conftest.py](tests/conftest.py).

Основные фикстуры:

- `setup_test_database` — создаёт тестовую схему БД один раз на запуск тестов;
- `db_session` — создаёт отдельную SQLAlchemy-сессию для каждого теста;
- `client` — создаёт FastAPI `TestClient` и подменяет зависимость БД на тестовую сессию;
- `ordinary_user` — создаёт обычного пользователя;
- `client_user` — создаёт пользователя и кладёт JWT в заголовок Authorization.

Почему это важно:

- тесты становятся независимыми;
- один тест не влияет на другой;
- не нужно вручную писать один и тот же подготовительный код в каждом тесте.

Пример:

```python
@pytest.fixture
def db_session():
    connection = engine.connect()
    transaction = connection.begin()
    session = TestingSessionLocal(bind=connection)
    yield session
    session.close()
    transaction.rollback()
    connection.close()
```

Это означает: каждый тест получает «чистую» БД и после теста откатывает все изменения.

### 3. Что такое factory

`factory_boy` — это фабрика объектов для тестов.

Она находится в [tests/factories/user.py](tests/factories/user.py).

Здесь есть `UserFactory`, который создаёт пользователя так:

```python
user = UserFactory.create(session=db_session, password="password")
```

Что делает фабрика:

- генерирует валидный email;
- генерирует phone;
- создаёт хеш пароля через тот же механизм, что и в приложении;
- привязывает создание к конкретной test-сессии;
- позволяет создавать объекты без повторения кода в каждом тесте.

То есть фабрика заменяет ручное создание сущностей вроде:

```python
User(phone="...", email="...", password_hash="...")
```

и даёт стабильный и читаемый способ генерации данных.

---

### 4. Что такое dependency override

Это подмена зависимостей внутри FastAPI.

В [tests/conftest.py](tests/conftest.py) есть такой фрагмент:

```python
app.dependency_overrides[db_dependency] = override_get_db
```

Что это значит:

- приложение обычно берёт БД через `db_dependency`;
- в тесте мы подменяем эту зависимость на тестовую сессию;
- благодаря этому endpoint видит именно тестовую БД, а не основную БД проекта.

Это один из ключевых механизмов для API-тестов.

---

### 5. Что такое TestClient

`fastapi.testclient.TestClient` позволяет отправлять HTTP-запросы в приложение как будто это реальный клиент.

Пример из [tests/test_auth.py](tests/test_auth.py):

```python
response = client.post(
    "/auth/login",
    json={"phone": user.phone, "password": "password"},
)
```

Тест проверяет:

- status_code;
- наличие `access_token` в ответе;
- сам токен не пустой.

То есть мы проверяем реальное поведение API, а не просто внутренние методы Python.

---

### 6. Важный принцип: разделять слои тестов

Удобно разделять тесты на два типа:

#### 6.1. Тест на состояние БД

Проверяет, что объект действительно сохраняется в БД.

Пример:

- создали пользователя через `UserFactory`;
- вызвали `db_session.commit()`;
- проверили, что в таблице появился нужный пользователь.

Это тест на persistence layer.

#### 6.2. Тест на API

Проверяет, что endpoint работает корректно.

Пример:

- создали пользователя;
- отправили запрос на `/auth/login`;
- проверили, что status_code == 200 и есть `access_token`.

Это уже контракт API.

Почему важно разделять:

- если упал БД-тест — проблема в модели / сохранении данных;
- если упал API-тест — проблема в endpoint / обработке запроса;
- проще локализовать ошибку.

### 7. Как писать хорошие тесты

Следующие правила помогут писать понятные и полезные тесты:

- один сценарий — один тест;
- тест на одно действие и одно ожидаемое поведение;
- используйте фикстуры для повторяющихся подготовок;
- используйте factory для генерации данных;
- проверяйте результат, а не внутреннюю реализацию;
- называйте тесты по смыслу, а не по техническим деталям.

Хорошее имя:

```python
def test_get_access_token_returns_jwt_for_valid_credentials():
    ...
```

Плохое имя:

```python
def test_login_1():
    ...
```

---

### 8. Почему в auth-тестах часто используется заглушка Redis и DAO

В реальном приложении auth-сервис обращается к:

- `UserDAO` для поиска пользователя по телефону;
- `RedisDependency` для хранения токена.

Но в тесте не нужно поднимать реальный Redis и не нужно гонять полноценный async-слой, если мы проверяем именно endpoint. Поэтому используют заглушки:

- `FakeRedis` — пустой объект, который умеет только методы `get` и `set`;
- `SessionUserDAO` — DAO поверх текущей SQLAlchemy-сессии.

Это позволяет проверить, что endpoint корректно работает, не заморачиваясь с внешними зависимостями.

---

### 9. Типичная ошибка новичков

Частая ошибка — создавать пользователя в одной сессии, а потом проверять его через другую.

Или создавать пользователя в фабрике, но не делать `commit()`, а затем ожидать, что endpoint увидит запись сразу.

Потому что:

- транзакция изолирована;
- изменения видны в той же сессии;
- в другом контексте они могут быть не видны до коммита.

Это нормально и это обычное поведение SQLAlchemy.

---

### 10. Какой правильный flow для теста

Обычно так:

1. подготовить данные через fixture/factory;
2. сохранить их в БД, если нужен реальный доступ через endpoint;
3. отправить HTTP-запрос через `TestClient`;
4. проверить `status_code` и тело ответа;
5. не проверять лишние детали реализации;
6. после теста транзакция откатывается автоматически.

---

### 11. Минимальный пример хорошего теста

```python
def test_get_access_token_returns_jwt_for_valid_credentials(client, db_session):
    user = UserFactory.create(session=db_session, password="password")
    db_session.commit()

    response = client.post(
        "/auth/login",
        json={"phone": user.phone, "password": "password"},
    )

    assert response.status_code == 200
    assert "access_token" in response.json()
```

Этот тест проверяет именно реальное поведение API и делает то, что нужно: он описывает, как система должна работать на входе и на выходе.

---

## Итог

Правильная практика в pytest такая:

- фикстуры отвечают за подготовку окружения;
- фабрики отвечают за генерацию сущностей;
- API-тесты проверяют поведение через HTTP;
- БД-тесты проверяют состояние данных;
- каждый тест должен отвечать на один ясный вопрос.

Это и есть суть тестирования: не «проверить код», а «проверить факт поведения системы».
